IMPLEMENTATION TASK A — UNIFY THE DEBT / CREDIT FORM

We have completed a detailed READ-ONLY audit of the current Debt/Credit creation flows.

The audit confirmed that the Home → آجل flow and Customer → إضافة آجل flow currently use two separate forms with duplicated UI/state logic.

The goal of this task is to extract the shared Debt creation UI/state into ONE reusable DebtForm component and make BOTH existing flows use it.

This task must remain tightly scoped.

==================================================
PRIMARY GOAL
==================================================

Create:

artifacts/retail-business-manager/components/DebtForm.tsx

and use this same component for:

1. Home → Quick Actions → آجل
2. Customer → إضافة آجل

The new DebtForm must contain the shared Debt-entry form behavior:

- Customer selection
- Amount
- Currency
- Optional dueDate

The component must use callback-based persistence.

Recommended contract:

onSave: (draft: {
  customerId: string;
  amount: number;
  currency: CurrencyCode;
  dueDate?: string;
}) => Promise<void>

The DebtForm must NOT directly access storage.

The DebtForm must NOT contain Firebase logic.

The DebtForm must NOT contain StoreContext persistence logic.

The DebtForm should be responsible for form UI/state/validation and pass the completed draft to its caller.

5. CRITICAL: HOME DUE DATE PERSISTENCE
==================================================

The READ-ONLY audit found an important existing limitation:

context/StoreContext.tsx

currently defines:

addCustomerDebt(...)

with a draft containing only:

{
  amount: number;
  currency: CurrencyCode;
}

It currently does NOT accept dueDate.

Because the new shared DebtForm contains an optional dueDate and will be used by the Home → آجل flow, this MUST be fixed as part of this task.

You MUST minimally extend addCustomerDebt so its draft accepts:

{
  amount: number;
  currency: CurrencyCode;
  dueDate?: string;
}

Then pass the optional dueDate through to the existing createDebt(...) call.

This is a required part of this task.

DO NOT silently discard a dueDate entered on Home.

The final data flow must be:

Home DebtForm
→ save callback
→ addCustomerDebt(...)
→ createDebt(...)
→ Debt.dueDate
→ existing storage

Existing callers that only provide:

{
  amount,
  currency
}

must continue working unchanged.

Do NOT change the Debt type.

Do NOT change storage keys.

Do NOT introduce another persistence mechanism.

Do NOT refactor StoreContext.

This must be a minimal signature extension only.

If dueDate is undefined or empty:

- preserve current behavior
- do not store an empty dueDate
- continue using the existing createDebt behavior
