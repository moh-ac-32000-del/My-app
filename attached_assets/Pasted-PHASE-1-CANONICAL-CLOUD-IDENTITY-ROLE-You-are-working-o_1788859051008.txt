==================================================
APPROVED FINAL WORKSPACE MODEL
==================================================

The final product model is:

Firebase Auth Identity
        ↓
User's Workspace Memberships
        ↓
Private Workspace + Shared Workspaces
        ↓
Currently Active Workspace
        ↓
Workspace-owned Firestore data

A user may belong to MULTIPLE Workspaces.

Example:

Mohammad
 ├── Mohammad's private Workspace
 └── Shared Workspace with Ahmed

Ahmed
 ├── Ahmed's private Workspace
 └── Shared Workspace with Mohammad

A Workspace is an independent data/security boundary.

A shared Workspace has its own data, and all authorized members see the
same Workspace data.

A user's private Workspace is separate from any shared Workspace.

IMPORTANT:
Phase 1 does NOT implement the UI or behavior for creating additional
Workspaces or switching between Workspaces.

Those remain separate future phases.

==================================================
CRITICAL MULTI-WORKSPACE CONSTRAINT
==================================================

DO NOT hardcode or assume that a user can belong to only one Workspace.

The existing path:

`users/{uid}/memberships/{spaceId}`

is a SUBCOLLECTION and inherently supports multiple Workspace memberships.

Therefore:

- Do not redesign it as a single Workspace field.
- Do not create a one-Workspace-per-user abstraction.
- Do not introduce code that assumes `primarySpaceId` is the user's only Workspace.
- Do not remove or bypass the existing memberships collection.
- Do not implement additional Workspace creation in this phase.
- Do not implement Workspace switching in this phase.

`primarySpaceId` may continue to represent the user's primary/default Workspace,
but it MUST NOT be interpreted as the user's only Workspace.

Phase 1 only needs to correctly establish/validate the CURRENT canonical
Workspace identity used by the authenticated session.

==================================================
CANONICAL IDENTITY RULES
==================================================

1. Firebase Auth UID is the authenticated user identity.

2. Workspace/Space is the canonical authorization and data boundary.

3. `spaceId` is independent from:
   - Firebase Auth UID
   - StoreProfile.id
   - StoreProfile.storeId

4. For the current MVP:
   Workspace = Store (1:1).

   Do NOT introduce multi-store-within-one-workspace behavior.

5. Authoritative membership is:

   `spaces/{spaceId}/members/{uid}`

6. User membership discovery is:

   `users/{uid}/memberships/{spaceId}`

   This is a discovery/index representation and must not replace
   authoritative membership.

7. `users/{uid}.primarySpaceId` identifies the user's primary/default Workspace.

   It does NOT mean the user can belong to only one Workspace.

8. Local `activeSpaceId` is a device preference/cache only.

   It is NOT proof of authorization.

9. The client must never trust a client-supplied UID as the authenticated identity.

10. The client must not become the authority for Workspace ownership or membership.

==================================================
ADMIN SDK SECURITY RULE
==================================================

IMPORTANT ARCHITECTURAL CONSTRAINT FOR THIS PROJECT:

Firebase Admin SDK bypasses Firestore Security Rules.

Therefore, any Cloud Function using Admin SDK for a protected operation MUST
independently enforce:

- request.auth exists
- authenticated UID comes from `request.auth.uid`
- Workspace membership is verified
- role/authorization is verified where applicable
- business invariants are validated
- sensitive writes use the appropriate trusted transaction/idempotency design

NEVER rely on Firestore Rules as authorization inside an Admin SDK Function.

Follow the established trusted pattern in:

`functions/src/bootstrapPrimarySpace.ts`

including the existing authentication assertion pattern such as:

`assertAuthenticated`

Do not weaken this security model.

NOTE:
Phase 1 is NOT a financial Cloud Function phase.
Do not expand `bootstrapPrimarySpace` into financial functionality.

SAME ACCOUNT / MULTIPLE DEVICES
==================================================

For Phase 1, the important requirement is:

The same Firebase Auth UID must resolve to the same canonical PRIMARY/DEFAULT
Workspace across devices.

Example:

Device A:
Firebase UID = USER-A
primarySpaceId = SPACE-A

Device B:
Firebase UID = USER-A
primarySpaceId = SPACE-A

Both resolve the same canonical default Workspace.

However, this MUST NOT be implemented as:

"one user can only ever have one Workspace."

The architecture must remain compatible with:

USER-A
 ├── SPACE-A (private/default)
 └── SPACE-SHARED (shared)

This phase only establishes the current/default Workspace.
It does not implement selecting SPACE-SHARED yet.
