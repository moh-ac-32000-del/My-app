PHASE 3B — CUSTOMER CLOUD CRUD + REAL-TIME LISTENER

GOAL:
Move CUSTOMER business data from local AsyncStorage to Firestore as the authoritative source of truth for the current canonical Workspace.

This phase is ONLY for Customers.

The Customer list MUST use a real-time Firestore listener (`onSnapshot`) so Customer changes are reflected across devices without requiring manual refresh.

IMPORTANT:
This is NOT a migration project.

Current local/test Customer data is disposable and does NOT need to be migrated.

==================================================
APPROVED ARCHITECTURE
==================================================

Firebase Auth UID
        ↓
Canonical Workspace / spaceId
        ↓
Firestore Customer collection
        ↓
spaces/{spaceId}/customers/{customerId}

Firestore is the authoritative source of truth for Customer business data.

AsyncStorage may remain for:
- UI preferences
- session state
- active Workspace preference
- drafts
- cache/device-local state

BUT:

AsyncStorage must NOT remain the authoritative Customer database after this phase.

Do NOT create two competing Customer sources of truth.

CURRENT CUSTOMER RULE SCHEMA
==================================================

The CURRENT deployed Firestore Rules validate Customer documents using the following implementation:

function isValidCustomerDocument(spaceId, customerId, customer) {
      return customer.keys().hasOnly([
          'id',
          'storeId',
          'workspaceId',
          'createdByUserId',
          'name',
          'phone',
          'address',
          'notes',
          'isActive',
          'createdAt',
          'updatedAt'
        ])
        && customer.id == customerId
        && customer.storeId is string
        && customer.name is string
        && customer.isActive is bool
        && customer.createdAt is string
        && customer.updatedAt is string
        && (!customer.keys().hasAny(['workspaceId']) || customer.workspaceId == spaceId)
        && (!customer.keys().hasAny(['createdByUserId']) || customer.createdByUserId is string)
        && (!customer.keys().hasAny(['phone']) || customer.phone is string)
        && (!customer.keys().hasAny(['address']) || customer.address is string)
        && (!customer.keys().hasAny(['notes']) || customer.notes is string);
    }

The Customer Rule block is currently:

match /spaces/{spaceId}/customers/{customerId} {
      allow read, delete: if isActiveMember(spaceId);
      allow create: if isActiveMember(spaceId)
        && isValidCustomerDocument(spaceId, customerId, request.resource.data)
        && (
          !request.resource.data.keys().hasAny(['createdByUserId'])
          || request.resource.data.createdByUserId == request.auth.uid
        );
      allow update: if isActiveMember(spaceId)
        && isValidCustomerDocument(spaceId, customerId, request.resource.data)
        && request.resource.data.id == resource.data.id
        && (
          (
            !resource.data.keys().hasAny(['workspaceId'])
            && !request.resource.data.keys().hasAny(['workspaceId'])
          )
          || (
            resource.data.keys().hasAny(['workspaceId'])
            && request.resource.data.keys().hasAny(['workspaceId'])
            && request.resource.data.workspaceId == resource.data.workspaceId
          )
        )
        && (
          (
            !resource.data.keys().hasAny(['createdByUserId'])
            && !request.resource.data.keys().hasAny(['createdByUserId'])
          )
          || (
            resource.data.keys().hasAny(['createdByUserId'])
            && request.resource.data.keys().hasAny(['createdByUserId'])
            && request.resource.data.createdByUserId == resource.data.createdByUserId
          )
        );
    }

IMPORTANT:
Do NOT modify firestore.rules in Phase 3B.

Do not weaken these Rules.

1. CUSTOMER READ — REAL-TIME
==================================================

Replace the current AsyncStorage Customer list loading with Firestore.

MANDATORY:

Use a real-time Firestore listener:

onSnapshot

for:

spaces/{spaceId}/customers

This is required for the project's multi-device architecture.

Do NOT implement Customer list loading using only:
- getDocs
- getDoc
- manual refresh
- screen-focus refresh

The listener must:

- subscribe to the canonical active Workspace
- update the Customer list when Firestore changes
- reflect changes made from another device/account with membership
- properly unsubscribe when the component/context unmounts
- properly unsubscribe when the active Workspace changes
- avoid duplicate listeners
- avoid stale listeners after authentication/session changes

Do not create an enterprise-wide realtime framework.

If inactive Customers are stored because of soft deletion, the normal Customer list should exclude:

unless the existing UI explicitly requires showing inactive Customers.

Do not create a new inactive-customer management UI in this phase.

==================================================
4. CUSTOMER DELETE — SOFT DELETE
==================================================

IMPORTANT ARCHITECTURAL DECISION:

The current application currently performs HARD DELETE locally.

However, the approved target architecture is:

Customer = SOFT DELETE.

Therefore Phase 3B MUST change Customer deletion semantics to:

isActive = false

and persist the Customer document in Firestore.

Do NOT delete the Firestore Customer document.

Do NOT call Firestore deleteDoc/remove for normal Customer deletion.

The Customer's historical identity must remain available for future historical references.

When soft deleting:

- preserve customer.id
- preserve storeId
- preserve workspaceId if present
- preserve createdByUserId if present
- set isActive = false
- update updatedAt

Do NOT delete or modify:
- Debts
- Payments
- Transactions
- Reminders
- Cash records

as part of this phase.

The default Customer list should not show inactive Customers unless existing UI behavior explicitly requires it.
