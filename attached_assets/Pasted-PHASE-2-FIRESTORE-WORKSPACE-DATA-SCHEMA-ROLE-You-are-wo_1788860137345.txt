PHASE 2 — FIRESTORE WORKSPACE DATA SCHEMA

ROLE

You are working on the existing Retail Business Manager Expo/React Native/
TypeScript project.

This is a tightly scoped ARCHITECTURE + DATA CONTRACT task.

The goal is to define and implement the minimal Firestore schema/path
contracts required for the approved Cloud-first Workspace architecture.

THIS PHASE MUST NOT MIGRATE FINANCIAL DATA.

==================================================
APPROVED FINAL MODEL
==================================================

The application uses:

Firebase Auth UID
        ↓
Workspace Memberships
        ↓
Active Workspace (`spaceId`)
        ↓
Workspace-owned Firestore data

A user may belong to multiple Workspaces.

Each Workspace is an independent data/security boundary.

Current MVP relationship:

Workspace = Store (1:1)

Do NOT implement multi-store-within-one-workspace.

Example future state:

USER A
 ├── PRIVATE WORKSPACE A
 └── SHARED WORKSPACE X

USER B
 ├── PRIVATE WORKSPACE B
 └── SHARED WORKSPACE X

Workspace X has ONE `spaceId`.

Both authorized users access the same Workspace data through that same
`spaceId`.

==================================================
PHASE 2 SCOPE
==================================================

Implement/define ONLY the Firestore data schema and path contracts.

This includes:

1. Workspace document path.
2. Authoritative membership document path.
3. User Workspace discovery/index path.
4. Workspace Store Profile path.
5. Canonical future paths for Workspace-owned business collections.
6. TypeScript contracts/constants/helpers needed to represent those paths
   safely and consistently.
7. Focused tests for path/schema correctness.

Do NOT implement actual financial data migration.

Do NOT copy existing AsyncStorage financial data into Firestore.

Do NOT create fake customers/debts/payments in production Firestore.

==================================================
CANONICAL PATH MODEL
==================================================

Use `spaceId` as the Workspace boundary.

The canonical structure should follow this conceptual model:

`spaces/{spaceId}`

    Workspace metadata

`spaces/{spaceId}/members/{uid}`

    Authoritative membership

`users/{uid}/memberships/{spaceId}`

    User-side discovery/index only

`users/{uid}`

    User account metadata such as primarySpaceId

Workspace-owned data should be under:

`spaces/{spaceId}/...`

Do NOT create top-level financial collections such as:

`customers/{id}`
`debts/{id}`
`payments/{id}`

for the new Cloud architecture.

Financial/business data must eventually be Workspace-scoped.

==================================================
WORKSPACE DOCUMENT
==================================================

Define the minimal canonical Workspace representation needed by the current
architecture.

It should remain compatible with the existing `Space` model and should not
duplicate unrelated business data.

At minimum preserve the established concepts:

- spaceId
- name
- mode
- status
- ownerUserId
- timestamps
- version where already established/appropriate

Do not invent unnecessary fields.

==================================================
MEMBERSHIP DOCUMENT
==================================================

The authoritative membership remains:

`spaces/{spaceId}/members/{uid}`

It must remain capable of representing multiple members in one Workspace.

Preserve the existing role/status model.

Do NOT implement role-management behavior in this phase.

Do NOT add custom permissions.

Do NOT add Partner/Employee UI.

==================================================
USER DISCOVERY INDEX
==================================================

Keep:

`users/{uid}/memberships/{spaceId}`

as the user's Workspace discovery/index representation.

It must support MULTIPLE membership documents.

Do not replace it with a single Workspace field.

`users/{uid}.primarySpaceId` means primary/default Workspace only.

It does NOT mean the user's only Workspace.

==================================================
STORE PROFILE
==================================================

The approved architecture keeps:

- Firebase UID
- `spaceId`
- `StoreProfile.id`
- `StoreProfile.storeId`

as separate identities.

Define the future Workspace-owned Store Profile path as:

`spaces/{spaceId}/storeProfile/profile`

The Store Profile must retain the separate business `storeId`.

Do NOT make `storeId` equal to `spaceId`.

Do NOT redesign StoreProfile unnecessarily.

Do NOT migrate the current local StoreProfile in this phase.

==================================================
FUTURE BUSINESS DATA PATHS
==================================================

Define canonical path contracts for future Workspace-owned collections.

Use the approved architecture as the basis:

`spaces/{spaceId}/customers/{customerId}`

`spaces/{spaceId}/debts/{debtId}`

`spaces/{spaceId}/payments/{paymentId}`

`spaces/{spaceId}/cashTransactions/{transactionId}`

`spaces/{spaceId}/dailyClosings/{closingId}`

`spaces/{spaceId}/reminders/{reminderId}`

`spaces/{spaceId}/notificationRecords/{notificationId}`

`spaces/{spaceId}/operationReceipts/{receiptId}`

`spaces/{spaceId}/auditEvents/{eventId}`

Only define the schema/path contracts required for this phase.

Do NOT implement CRUD or migration for these collections.

Do NOT add unnecessary fields or indexes unless required by the schema
contract.

==================================================
CRITICAL SPACE ISOLATION RULE
==================================================

Every Workspace-owned business document must be addressable by its
canonical `spaceId`.

The schema must make this possible:

Workspace A:
`spaces/SPACE-A/customers/...`

Workspace B:
`spaces/SPACE-B/customers/...`

Shared Workspace X:
`spaces/SPACE-X/customers/...`

If Mohammad and Ahmed are members of SPACE-X, they must eventually read the
same documents under SPACE-X.

Mohammad's private Workspace data must remain under Mohammad's private
`spaceId` and must not be mixed with SPACE-X.

==================================================

==================================================

Do NOT introduce new top-level financial/business collections.

Do NOT create a schema where authorization depends on a client-provided
`storeId`.

The Workspace boundary is `spaceId`.

`storeId` remains a separate business identity.
