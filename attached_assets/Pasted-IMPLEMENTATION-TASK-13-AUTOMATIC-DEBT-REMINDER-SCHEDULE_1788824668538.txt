IMPLEMENTATION TASK #13 — AUTOMATIC DEBT REMINDER SCHEDULE FOUNDATION

GOAL

Connect the existing optional Debt dueDate to the existing Reminder storage foundation.

This task introduces:

1. A global notification/reminder time setting.
2. Automatic generation of reminder records from a debt's dueDate.
3. Deterministic reminder scheduling based on the due date and global reminder time.

IMPORTANT:

This task does NOT implement actual Push Notifications.

It does NOT implement Notification Center.

It does NOT implement weekly overdue reminders.

It does NOT implement WhatsApp reminder behavior.

It does NOT implement the 9 PM follow-up flow.

Those will be separate tasks.

The purpose of this task is to create and verify the business/data foundation that determines WHEN reminders should exist.

==================================================
CURRENT ARCHITECTURE — DO NOT BREAK
==================================================

The app is local-first.

Financial data remains local.

Existing Reminder storage already exists.

Current Reminder model:

ReminderStatus = 'pending' | 'completed' | 'dismissed'

Reminder:

- debtId: string
- remindAt: string
- status: ReminderStatus
- note?: string
- completedAt?: string

Reminder records are stored through the existing space-aware storage layer.

Debt currently contains:

- customerId
- currency
- amount
- dueDate?: string
- originalAmount?
- settledAt?

Debt dueDate is stored as:

YYYY-MM-DD

Task #12 has already replaced the free-text due-date input with a native date-only calendar picker.

DO NOT REGRESS THAT IMPLEMENTATION.

SCOPE
==================================================

This task has TWO tightly related parts:

PART A — GLOBAL REMINDER TIME SETTING

Add a local global setting for the default debt-reminder notification time.

Default:

09:00

The setting must be:

- local
- persistent
- editable from Settings → Notification Settings
- represented as a valid 24-hour HH:mm value

IMPORTANT:

This is the DEFAULT TIME used when generating reminder records.

It is NOT a per-debt time.

Do NOT add a time picker to DebtForm.

DebtForm must continue to contain DATE ONLY for due date.

The reminder time belongs to Notification Settings only.

PART B — AUTOMATIC REMINDER GENERATION

When a debt has an optional dueDate, generate the appropriate reminder record(s) automatically according to the agreed reminder rules.

For the current foundation task, implement ONLY the immediate due-date reminder schedule:

- One reminder for the debt's due date.
- remindAt uses the configured global reminder time.
- If no dueDate exists, no reminder is generated.
- If the debt is already settled when the schedule is generated, do not create a pending reminder.
- The generated Reminder must reference the correct debtId.
- The generated Reminder must belong to the active local space/store.

Do NOT implement:
- 3-day-before WhatsApp reminders
- 3-day Push notifications
- weekly overdue reminders

- Firebase notification logic

==================================================
REMINDER GENERATION
==================================================

Create a small deterministic business function/service responsible for generating the due-date reminder.

It should be easy to test without rendering UI.

Conceptually:

Debt + notification time
→ optional Reminder draft

Rules:

1. Debt without dueDate:
   return no reminder.

2. Debt with dueDate and amount > 0:
   produce one pending reminder for the due date at the global reminder time.

3. Settled debt:
   do not produce a pending due-date reminder.

4. The reminder must use:
   debtId = debt.id

5. Do not create duplicate pending reminders for the same debt and same scheduled remindAt.

6. Existing reminders must not be deleted blindly.

7. If the debt's dueDate changes, the old pending due-date reminder must not remain pointing to the old date.

8. If the global notification time changes, future pending due-date reminders should be recalculated only if that is necessary to keep them aligned with the new global setting.

IMPORTANT:

Do not implement a background scheduler in this task.

Do not create timers or intervals.

Do not use setInterval/setTimeout for reminder scheduling.

A Reminder record represents the scheduled business event.

Actual delivery will be implemented later.

==================================================
UPDATE / DELETE / SETTLEMENT SAFETY
==================================================

Inspect the existing debt update, settlement, and deletion behavior.

The new reminder foundation must not create stale pending reminders.

At minimum:

- Creating a debt with no dueDate → no reminder.
- Creating a debt with dueDate → one reminder.
- Updating a debt from no dueDate → dueDate → create reminder.
- Changing an existing dueDate → update/reconcile the pending reminder.
- Removing dueDate → remove/cancel the associated pending due-date reminder.
- Settling the debt → associated pending due-date reminder must no longer remain pending.

IMPORTANT:

Do not redesign debt settlement.

Do not redesign debt deletion.

Use the existing storage/business flows and make only the minimum reminder reconciliation needed.

Do not delete completed/dismissed historical reminders unnecessarily.

==================================================
DUPLICATE PROTECTION
==================================================

Reminder generation must be idempotent.

Calling the generation/reconciliation function twice for the same unchanged debt must NOT create duplicate pending reminders.

Example:

Debt:
id = debt-123
dueDate = 2026-09-30
notification time = 09:00

First reconciliation:
→ one pending reminder

Second reconciliation:
→ still one pending reminder

NOT:

→ two reminders

==================================================
DATE / TIME SAFETY
==================================================

This is a critical requirement.

Due dates are calendar dates, not UTC timestamps.

Do NOT convert YYYY-MM-DD to a UTC timestamp in a way that can shift the calendar date.

Do not use:

new Date(`${dueDate}T...Z`)

or:

toISOString().slice(0, 10)

for calendar-date persistence.

Use local calendar components where appropriate.

The generated reminder must correspond to the user's intended local date and configured local notification time.

Inspect existing date utilities before introducing a new one.

Avoid duplicate date utilities if an existing safe helper can be reused.
