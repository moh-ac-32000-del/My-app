PHASE 3B — CUSTOMER CLOUD CRUD

GOAL:
Move CUSTOMER business data from local AsyncStorage to Firestore as the authoritative source of truth for the current canonical Workspace.

This phase is ONLY for Customers.

IMPORTANT ARCHITECTURE:
- Firebase Auth UID is the authenticated identity.
- Workspace/spaceId is the security and data boundary.
- The canonical Workspace comes from Phase 1 cloud bootstrap.
- Firestore is the authoritative source for Customers.
- AsyncStorage must NOT remain the authoritative source for Customers after this phase.
- Current local/test data is disposable. DO NOT build a migration system.
- Do NOT preserve old local customer records through migration.
- Local storage may remain for UI preferences/session/cache/drafts only, but NOT as the primary Customer database.

==================================================
READ
==================================================

Replace the Customer authoritative read path with Firestore.

For the currently selected canonical Workspace:

spaces/{spaceId}/customers

Read only the Customers belonging to that Workspace.

Do not read a top-level customers collection.

Do not load customers from every Workspace.

Do not use an unbounded cross-workspace query.

If the current UI needs the complete customer list, use the Workspace-scoped collection.

If pagination is necessary because of the current implementation, keep it simple and bounded.

Do not introduce a large pagination framework.

==================================================
CREATE
==================================================

When creating a Customer:

- Generate/use the existing Customer ID mechanism if compatible.
- Write to:
  spaces/{spaceId}/customers/{customerId}
- Ensure document id == customer.id.
- Preserve existing storeId semantics.
- workspaceId, if used by the existing model/rules, must match the canonical spaceId.
- createdByUserId, if used, must come from authenticated Firebase Auth context, not user input.
- createdAt/updatedAt should use the existing timestamp semantics.
- Do not accept an arbitrary client-provided authorization identity.
- Do not write to AsyncStorage as the authoritative Customer record.

Use the existing customer creation flow as much as possible.

==================================================
UPDATE
==================================================

When updating a Customer:

- Update the Firestore document under the same Workspace.
- Preserve customer.id.
- Do not allow the update to move the document to another Workspace.
- Preserve createdByUserId if the current model/rules require it.
- Update updatedAt appropriately.
- Do not silently overwrite unrelated fields.
- Do not create a second Customer document.

Use the existing UI and customer editing flow.

==================================================
DELETE
==================================================

Implement the existing Customer delete operation against Firestore.

Do not introduce a new deletion policy in this phase.

Do not delete debts/payments/transactions/etc. as part of Customer deletion.

Only delete the Customer document requested by the existing Customer delete flow.

The current Phase 3A Rules already authorize Customer deletion for active Workspace members. Do not broaden that authorization.

==================================================
ERROR HANDLING
==================================================

Important:

If Firestore is unavailable or the request fails:

- Do NOT silently fall back to local AsyncStorage Customer data.
- Do NOT present stale local Customers as authoritative data.
- Surface a clear error to the existing UI where appropriate.

Financial/customer cloud architecture must not create two competing sources of truth.

If Firebase is not configured in a test environment, use the smallest testable abstraction possible, but do not introduce production fallback behavior.
