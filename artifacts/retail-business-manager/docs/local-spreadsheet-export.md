# Local spreadsheet export — My app

Repository: `moh-ac-32000-del/My-app` only. This is a user-initiated XLSX review export for Excel and manual Google Sheets import. It is not a restorable backup, an offline ledger, a new financial source, a Google Drive connection or an automatic upload.

## Zero additional data reads on export

The initial read-only callable proposal was removed before commit/deployment at the user's explicit request. There is no new callable, backend function, Firestore query, refresh, prefetch, subscription or scheduler in the export path. Existing customer/debt/payment/cash listeners copy their already-delivered full collection snapshots into a bounded in-memory session cache. Metadata events are included on those same listeners so a server-confirmed empty collection is distinguishable from an incomplete cache result; this does not add another subscription. Existing screen loading, reconnects and ordinary synchronization can still incur normal Firestore reads. No claim is made that the application as a whole is free of reads.

Archive list responses already requested by normal application screens are copied too. A single newly closed archive response is not treated as a full archive list. Store-specific archive coverage is checked independently from workspace-wide collections. No reads are performed to fill gaps when exporting.

Each account/workspace is isolated. Snapshots received from cache only, pending writes, unknown metadata, terminal errors and over-limit sections are not treated as complete source sections. The UI shows which of nine sections are missing and disables export until all are available. It does not silently substitute zero or export the first subset. Existing screen visits are needed to receive missing sections and those normal visits can incur reads. The cache is session-only, not a durable local backup; restarting/signing out requires receiving sections again. Authentication transitions clear the cache before exposing the new session, and late old-account callbacks cannot populate another account's cache.

Data from different sections may have different capture times. The file lists each time in UTC and its export creation time separately. It is **not** an atomic or guaranteed-current Firebase snapshot. No live membership revalidation is performed by the export button; it copies only data already delivered under the existing application's access rules. There is no new server-side owner/admin export permission claim. Firebase remains the financial source of truth.

## Contents and validation

Version 2 downloads three worksheets: Customer statement, Merchants, and Cash and closings. The legacy version 1 two-sheet renderer remains compatible with existing fixtures. The seven old typed tables and metadata are a validation intermediate, not additional downloaded tabs. Exact scoped account data supplements them in version 2. Deactivated customers/merchants and settled debts are not omitted. Optional missing original debt amounts/legacy closing balances remain unavailable, not fabricated zero. Different currencies are never summed or converted; payments, cash and archived events are separate views, not additive postings. No backend balance formula is changed by export.

### Reader-facing report

The workbook opens on Customer statement. Each customer has their own block with name, phone, status, address/notes, a signed current balance per currency, and chronological debt/payment history. Current balances use exact remaining debts minus current customer credit, never subtracting old payment records again. Customers with credit and no outstanding debt remain visible. Each debt shows its recorded original amount (blank if unknown), exact remaining amount, note and due date. Direct customer-to-merchant payments are explicitly noncash and carry the recorded merchant name. Payments do not invent historical per-payment balances. Duplicate names stay separate by customer ID; missing customer metadata and unlinked payments remain visible.

Merchants has separate payables/store-credit/net totals per currency, then one block per merchant with name/phone/status, current balances and every loaded operation. Purchases include original material quantities, unit prices and per-line totals. Each operation retains exact primary amount, actual signed cash effect, merchant balance before/after, customer name when applicable, note and hidden operation/actor IDs. This is a review of stored operations, not a new accounting source.

Cash and closings contains one cash-movement section, followed by a block per closing with date/number, closing time, event count, recorded currency balances and chronological historical events. Missing legacy balances are explicitly unavailable, not zero. Historical event names are preserved. Cash movements and archived events are never summed together. Source/capture-time notes are at the foot of both worksheets, not a third metadata tab. Original IDs and source type are retained in hidden trailing columns for tracing.

All authored headings, statuses, payment methods/directions, event types, currency names and source text follow the app language (Arabic, English or Turkish) passed at export time. ISO currency codes and UTC remain explicit for precision. User-entered names, addresses and notes are never machine-translated. Numeric amounts and sortable date cells are unchanged. Technical metadata and per-section capture times remain available at the end; this changes presentation only and does not add reads or change the local data contract.

There is a 1,000-record limit per captured section, 10,000 expanded archive rows and a bounded projected payload. Invalid/mismatched records and unsupported dates fail the export rather than disappear from it. The file intentionally excludes authentication data, passwords, Firebase keys, Push tokens, membership lists and internal receipts. It is not suitable for full application restoration.

Workbook text is explicitly typed as strings, including formula-looking notes, phone numbers and IDs; no formulas/hyperlinks/macros/external connections are generated. Representable ordinary amounts remain numeric with a format that shows their actual fraction. Values beyond Excel's 15-significant-digit range, long integer/deep-fraction values and subnormal legacy fractions are literal full decimal text, not rounded numeric mirrors. A visible explanation distinguishes these cells. Date cells remain numeric and sortable UTC/date-only values. Existing SheetJS 0.20.3 and its lockfile are unchanged; no export-library migration or new dependency is introduced.

## Complete merchant-history coverage

The approved policy blocks incomplete reports. The nine required sections are customers, debts, payments, transactions, dailyArchives, customerCredits, merchants, merchantBalances and merchantOperations. Existing scoped account listeners supply metadata/balances/credits; already requested statement queries/pages supply operations, including their already received lookahead document. There are no new export subscriptions or count queries.

For the trusted version-1 merchant schema, each financial command increments exactly one merchant/currency balance revision and creates exactly one immutable operation. Metadata edits and receipt replay do neither. Received unique operation counts must match every merchant/currency revision; duplicate balance keys, unknown scope, missing originals/corrections and incomplete pages block export. A staged backend regression verifies this invariant across opening, purchase, cash/external/direct payment, reversal, metadata edit and replay. If the schema changes, adapt this coverage proof rather than assuming new revisions mean the same thing.

Received pages are unioned in session memory, preserving immutable payload checks and reversal links. A new balance without its operation (or vice versa) makes the report unavailable until matching observations arrive. A confirmed empty merchant/balance pair needs no history query. The 1,000-operation bound also applies to the combined merchant history; higher required revision totals fail as too large, not as an export of the first pages. Epoch/user/scope guards bind asynchronous page observations before awaiting a read, so late old-session pages cannot populate the current export. Bidirectional linked cash/payment/correction-debt consistency is validated again before creating bytes.

## Saving and confidentiality

Explicit inline confirmation warns that the file is readable, unencrypted financial/personal data. Android uses the system folder chooser, creates a new file and verifies full read-back before reporting success. A failed write only attempts to remove the newly created incomplete file, never an existing user file. A storage provider that refuses verification results in failure, not a false success. Device/provider support determines available USB/SD folders; the user can also move the saved file later. No broad storage permission is requested.

iOS opens the share/save sheet and reports only that handoff, not confirmed retention. Its temporary app-cache copy is removed afterward. Web requests a normal browser download and does not claim download completion. Scope/account guards stop stale exports before file operations. Test native APIs are mocked; actual Android directory/USB/SD behavior must be checked in the single combined APK later.

For Google Sheets the user manually uploads the local XLSX to Google, with the associated disclosure of its contents. There is no automatic transfer or account integration. Keep copies outside the phone in secured storage. XLSX export does not replace the postponed Firebase backup/PITR plan or the separately pending encrypted/restorable local backup feature. No EAS build or paid cloud protection is enabled by this change.
